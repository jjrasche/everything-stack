# Memory Encoder Pipeline

## Glossary

| Term | Definition |
|------|-----------|
| **Memory System** | The complete module. Encoder + working memory + knowledge store + entity resolution + consolidation. Input: source texts. Output: structured, entity-linked, temporally-versioned knowledge. |
| **Encoder** | The pipeline: normalize → segment → cohere → recohere → filter → decontextualize → dedup. Input: source (sourceId + texts array) + working memory state. Output: working memory diff. Scope ends at working memory. |
| **Source** | Raw input to the encoder. A `sourceId` plus an array of text strings. The pipeline never looks inside the strings or cares where they came from. Source-agnostic. |
| **Sentence** | Atomic text unit from segmentation. Verbatim from source. Identified by `S1`, `S2`, etc. per text position. |
| **Concept Span** | One or more sentences grouped by discourse coherence. The unit that filter scores and decontext decomposes. |
| **Proposition** | Self-contained, decontextualized knowledge unit. Encoder output. Contains content + sourceIds + scope + type. No pronouns, no inline provenance. Lives in working memory. |
| **Fact** | A proposition after entity resolution and persistence. Proposition + entity links + temporal metadata. Lives in the knowledge store. Not built yet. |
| **Working Memory** | Bounded set of propositions relevant to the current processing context. Versioned via event-sourced diffs. The encoder reads from and writes to working memory. |
| **Knowledge Store** | All persisted facts with entity links and temporal metadata. Long-term memory. Append-only with supersession. Not built yet. |
| **Entity Resolution** | Links entity mentions in propositions to entities in the knowledge store. Post-encoder, converts propositions to facts. Not built yet. |
| **Working Memory Diff** | The output of one encoder run. `{added, archived, superseded, rewritten}`. Applied to working memory by the caller. |

## Pipeline Overview

```
Source Texts → [1.Normalize] → [2.Segment] → [3.Cohere] → [4.Recohere] → [5.Filter] → [6.Decontext] → [7.Dedup] → WM Diff
                   SLM 210M        regex          SLM 110M     SLM 110M       SLM 44M      LLM 8B         SLM 22M
```

**Input**: Source (sourceId + texts array) + current working memory state
**Output**: Working memory diff `{added, archived, superseded, rewritten}`

## Source-Agnostic Principle

**The encoder processes text. It does not know where the text came from.** No speakers, no turns, no prompts, no responses. The pipeline input is `{sourceId, texts: [string, string, ...]}`. Array position is identity. Evaluation rubrics, filter labels, decontext decomposition, and dedup comparisons all treat text identically.

### Bare Assertive Form

Propositions are facts in waiting. They must be written in **bare assertive form**: the claim itself, with no epistemic framing. No "The user...", "The assistant explained...", or any attribution wrapper. Provenance is metadata on the source record, not part of the proposition content.

A proposition reads like a fact about the world, not an observation about a person.

| Wrong (epistemic framing) | Right (bare assertive) |
|---|---|
| "The user wants to use ObjectBox for persistence" | "ObjectBox is the chosen persistence layer" |
| "The user prefers JSON for storing incidents" | "Incidents are stored in JSON format" |
| "The user decided against EC2" | "EC2 was rejected for the therapy tracker" |
| "The assistant explained that PWAs update automatically" | "PWAs update automatically via background browser checks" |
| "The user recognizes a conflict between helping and an emotional counter-impulse" | "A conflict exists between wanting to help children and an emotional counter-impulse" |

**Why**: The knowledge store will contain thousands of propositions linked to entities, projects, and domains. "The user wants X" pollutes every query with attribution noise. "X is the case" is the knowledge itself. Provenance is tracked by `sourceId` and array position.

**Test**: If you prefix "It is known that..." to a proposition and it reads naturally, it's in bare assertive form. "It is known that ObjectBox is the chosen persistence layer" works. "It is known that the user wants to use ObjectBox" does not.

## Golden Data Generation

**Claude Code generates ALL golden data.** No Groq, no external LLM APIs. Claude Code reads prior stage output, applies the stage's Operation + Evaluation Rubric, writes ground truth JSON.

**Separate concerns:**
- **Golden data** = ground truth generated by Claude Code for each stage
- **SLM accuracy testing** = Dart scripts run on-device models, compare output against golden ground truth

### Corpus
33 golden sources in `golden/sources/`. Converted from `golden/turns/` by `scripts/prepare_sources.py`.

### Pipeline Input Format

```json
{
  "sourceId": "<uuid>",
  "texts": [
    "first chunk of text to process",
    "second chunk of text to process"
  ]
}
```

`sourceId` links to provenance. `texts` is an array of strings. Array position is identity.

### Stage Output Format

Each stage writes one file per source to `<stage>_output/<sourceId>.json`:

```json
{
  "sourceId": "<uuid>",
  "stage": "normalize",

  "generatedAt": "ISO-8601",
  "results": [
    {"input": {...}, "output": {...}},
    {"input": {...}, "output": {...}}
  ]
}
```

`results` is a parallel array matching `texts`. Position 0 in results = processing of position 0 in texts.

Key points:

### Processing Rules
1. Process sources sequentially (sorted by UUID).
2. Each source's dedup runs against working memory reconstructed from prior sources' unified run diffs.
3. Stages write intermediate files during generation. The assembly script merges them into the unified format.
4. Latency fields are 0 for golden data.

### Cross-Source State

Most stages are stateless per source. Two exceptions:
- **Decontext**: Entity list accumulates from generated propositions. Starts empty per source.
- **Dedup**: Reconstructs working memory from unified run diffs of all prior sources. First source starts with empty WM. Second source's dedup compares against the first source's surviving propositions. No separate WM cache file. Sources are processed sequentially for this reason.

### Generation Architecture

One `claude --print` agent per stage per source. 7 agents run sequentially. Each agent:
1. Reads the prior stage's output (stripped to minimal required fields).
2. Applies the stage's Generation Prompt from this doc.
3. Writes output JSON to the stage's output directory.
4. Must pass the heuristic gate before the next agent launches.

After all 7 stages pass, the assembly script (`scripts/assemble_golden.py`) merges per-stage files into the unified run format and computes heuristics and metrics.

Intermediate stage files are working artifacts. The unified run JSON is the deliverable.

### Status

**Unified runs completed**: 6/33 sources have full pipeline output in `unified_runs/`.

### Pipeline-First Workflow

One source at a time through ALL 7 stages. Heuristic gates between stages. Hard stop on red flags.

#### Input Sizing
- Calculate token count from `source["texts"]`.
- If > 6000 tokens, split the source. Remaining texts become a second batch.

#### Orchestration
Run `scripts/golden_pipeline.py <uuid_prefix> [--resume] [--from-stage <stage>]`:
1. Load source from `sources/<uuid>.json`.
2. Reconstruct working memory from unified run diffs of prior sources (if any).
3. For each stage (normalize through dedup):
   - Build agent prompt with prior stage output + generation rubric from this doc.
   - Launch `claude --print` agent via subprocess.
   - Agent writes output JSON to stage directory.
   - Run `scripts/golden_heuristics.py` on output.
   - Red flag = hard stop.
4. After all 7 stages pass, launch qualitative review agent.
5. Run `scripts/assemble_golden.py` to merge per-stage files into unified run format.
6. Assembly script computes heuristics, metrics, writes unified JSON.

Flags:
- `--resume`: Skip stages whose output already exists and passes heuristics.
- `--from-stage X`: Resume stages before X, regenerate X and all later stages. Use after manually editing a stage's output.

#### Heuristic Gate Philosophy
- Per-instance metrics (per text, per span). Not aggregate.
- Computable from output JSON alone. No LLM needed.
- Red flag = process error. Not a tuning mechanism.
- Bug checks (epistemic_rate = 0%) are separate from health ranges.
- Thresholds calibrated from first pipeline run, updated as needed.

## Stage 1: Normalize

**Question**: Is this text clean enough to segment?

**Two-phase operation**:

**Phase A — Deterministic markdown stripping** (`scripts/markdown_strip.py`): Runs before any LLM/SLM sees the text. Converts structured markdown elements to clean prose suitable for sentence segmentation. Order of operations:
1. Remove XML tags (`<antThinking>`, etc.)
2. Remove fenced code blocks (` ``` ... ``` `)
3. Remove indented code blocks (4+ space indent after blank line)
4. Convert markdown tables to row-per-sentence prose (`RowLabel -- Header1: Value1. Header2: Value2.`)
5. Convert bullet lists to comma-delimited prose with Oxford comma (`A, B, and C.`)
6. Convert numbered lists to sequential sentences (`Do A. Do B. Do C.`)
7. Strip bold/italic markers (including orphaned `**`)
8. Strip header markers (`#` through `######`)
9. Strip inline code backticks
10. Strip markdown links, keep link text
11. Collapse excessive whitespace

Each transform is a leaf function. The orchestrator `strip_markdown()` calls all 11 in sequence. Tested by 46 unit tests + integration test on all 33 golden sources.

**Phase B — Punctuation and truecasing**: Compute punctuation ratio (marks per word). If below threshold (AdaptationState: `punctuationRatioThreshold`), invoke SLM for punctuation restoration + truecasing. Then check for overlong sentences exceeding word limit (AdaptationState: `maxSentenceWords`, default 40). Split at coordinating conjunctions: `, and `, `, but `, `, so `, `, or ` when preceded by a subject-verb clause.

#### Input
```json
{
  "text": "so we decided to use objectbox because it supports all six platforms and the single writer model means we need queue coordination for concurrent writes"
}
```

#### Output
```json
{
  "text": "So we decided to use ObjectBox because it supports all six platforms. The single writer model means we need queue coordination for concurrent writes.",
  "punctuationNeeded": true,
  "latencyMs": 16
}
```

#### Metrics (per text)
| Metric | Formula | Healthy | Red Flag |
|--------|---------|---------|----------|
| `punctuation_ratio` | punctuation marks / word count | 0.05-0.125 | < 0.04 or > 0.33 |
| `max_sentence_words` | longest sentence word count | 10-35 | > 50 |


#### Generation Prompt (Golden Data)

```
Read each source text. Normalize independently.
Markdown formatting, code blocks, tables, and XML tags have already been stripped (Phase A).

Rules:
- Compute punctuation ratio (punctuation marks / word count).
- If ratio < 0.05: add punctuation and truecasing.
- Check for sentences exceeding 40 words. Split at coordinating conjunctions (, and / , but / , so / , or).
- Clean STT artifacts and filler words.
- Preserve all factual content. Do not rephrase or summarize.

Input: pre-cleaned texts array (markdown already stripped).
Output: results array, one entry per text. Each entry: normalized text + punctuationNeeded flag.
```

#### Review Screen
Source text on top, normalized text on bottom. Each change (inserted punctuation, case change, split point) highlighted individually. Tab through changes one at a time: accept or reject each. Each decision = one training pair. Arrow keys to advance to next source. Instances with metrics outside healthy range surfaced first.

#### Implementation
**Phase A**: `scripts/markdown_strip.py` — pure Python, no dependencies. 11 regex-based transforms. Tests: `scripts/test_markdown_strip.py` (46 unit), `scripts/test_integration_strip.py` (integration on all golden sources).
**Phase B Model**: `1-800-BAD-CODE/punctuation_fullstop_truecase_english` (210M ONNX, SentencePiece 32k vocab).
**AdaptationState**: `punctuationRatioThreshold` (float), `maxSentenceWords` (int, default 40).

#### Training
**Phase A**: No training needed (deterministic rules). Extend transforms if new markdown patterns appear in sources.
**Phase B Fine-tuning**: Trigger: >5% correction rate across 50+ reviewed instances. Golden data: accumulated (source, corrected) pairs from review. Expected improvement: domain-specific truecasing (ObjectBox, DeBERTa, HNSW).

## Stage 2: Segment

**Question**: What are the atomic sentence units in this text?
**Operation**: Strip code blocks (fenced + indented), strip markdown formatting, split on sentence boundaries (`.?!`), filter fragments under minimum word count (AdaptationState: `minFragmentWords`, default 3).

#### Input
```json
{
  "text": "So we decided to use ObjectBox because it supports all six platforms. The single writer model means we need queue coordination for concurrent writes."
}
```

#### Output
```json
{
  "sentences": [
    {"id": "S1", "text": "So we decided to use ObjectBox because it supports all six platforms."},
    {"id": "S2", "text": "The single writer model means we need queue coordination for concurrent writes."}
  ],
  "latencyMs": 1
}
```

#### Metrics (per text)
| Metric | Formula | Healthy | Red Flag |
|--------|---------|---------|----------|
| `avg_sentence_words` | total words / sentence count | 8-25 | < 4 or > 40 |


#### Generation Prompt (Golden Data)

```
Read the normalized text for each text position. Segment into sentences.

Rules:
- Strip code blocks (fenced and indented). Strip markdown formatting.
- Split on sentence boundaries (.?!).
- Filter fragments under 3 words into droppedFragments.
- Each sentence gets a sequential ID: S1, S2, S3, etc. Reset per text position.
- Numbered list items ("1. Do this") are sentences. The bare number alone ("1.") is a dropped fragment.

Input: normalized texts from results array.
Output: results array, one entry per text. Each entry: sentences array + droppedFragments array.
```

#### Review Screen
Source text with split boundaries marked as colored bars between sentences. Reviewer clicks a boundary to remove it, clicks between words to add one. Arrow keys to advance. Flag instances where avg sentence length is outside range.

#### Implementation
Pure regex. Deterministic. No model.
**AdaptationState**: `minFragmentWords` (int, default 3).

#### Training
No model. Rule updates only from review disagreements (e.g., abbreviation periods).

## Stage 3: Cohere

**Question**: Which adjacent sentences are part of the same thought?
**Operation**: Score each adjacent sentence pair for discourse continuity via pairwise SLM inference. Pairs scoring below boundary threshold (AdaptationState: `cohereBoundaryThreshold`, default 0.5) mark topic boundaries. Group consecutive same-topic sentences into concept spans. Resplit any span exceeding max sentence count (AdaptationState: `maxSpanSentences`, default 15) at weakest internal boundary below resplit threshold (AdaptationState: `resplitThreshold`, default 0.65).

#### Input
```json
{
  "sentences": [
    {"id": "S1", "text": "So we decided to use ObjectBox..."},
    {"id": "S2", "text": "The single writer model means..."},
    {"id": "S3", "text": "OK anyway what about the UI?"},
    {"id": "S4", "text": "The button placement feels wrong."}
  ]
}
```

#### Output
```json
{
  "spans": [
    {"spanId": "span_0", "sentenceIds": ["S1", "S2"]},
    {"spanId": "span_1", "sentenceIds": ["S3", "S4"]}
  ],
  "pairScores": [
    {"pair": ["S1", "S2"], "coherenceScore": 0.89, "boundary": false},
    {"pair": ["S2", "S3"], "coherenceScore": 0.31, "boundary": true},
    {"pair": ["S3", "S4"], "coherenceScore": 0.84, "boundary": false}
  ],
  "latencyMs": 9
}
```

#### Metrics (per text)
| Metric | Formula | Healthy | Red Flag |
|--------|---------|---------|----------|
| `avg_span_words` | word count per span | 15-150 | < 5 or > 300 |
| `avg_span_sentences` | sentences per span | 2-8 | all 1-sentence spans or > 15 |


#### Generation Prompt (Golden Data)

```
Read the segmented sentences for each text position. Group adjacent sentences into concept spans.

Rules:
- Group adjacent sentences discussing the SAME concept/topic.
- Split when the topic shifts: costs to labor, design to metrics, proposal to follow-up.
- Spans cannot cross text boundaries.
- Sequential IDs: span_0, span_1, etc. Reset per text position.
- Each span lists its sentence IDs.

Splitting guidance:
- When a long passage covers a broad topic ("system features"), split by sub-topic.
- BAD: One span with 8 sentences covering trip tiers + credit mechanics + access controls.
- GOOD: span_0 (trip tiers), span_1 (credit mechanics), span_2 (access controls).
- When sentences shift from one aspect to another, that is a boundary even if the broad topic is the same.

Do NOT impose a hard sentence limit. Let coherence drive the boundaries.
A 6-sentence span about one concept is fine. A 3-sentence span mixing two concepts is wrong.

Input: sentences array per text position.
Output: results array, one entry per text. Each entry: spans array (spanId + sentenceIds).
```

#### Review Screen
First sentence on top, second sentence on bottom. Coherence score displayed between them. Current decision (boundary/continuation) pre-selected as tab. Reviewer switches tab to change. Left/right arrow keys to advance to next pair.

#### Implementation
**Model**: `bert-wiki-paragraphs` (110M ONNX, WordPiece tokenizer). Pairwise scoring, ~3ms/pair.
**AdaptationState**: `cohereBoundaryThreshold` (float, default 0.5), `resplitThreshold` (float, default 0.65), `maxSpanSentences` (int, default 15).

#### Training
**Fine-tuning**: Trigger: >10% correction rate across 50+ reviewed pairs. Golden data: (sentence_a, sentence_b, should_be_boundary) from review. Expected improvement: boundary F1 from ~85% to 92%+.

## Stage 4: Recohere

**Question**: Are there non-adjacent spans within this source that belong together?
**Operation**: Compute pairwise cosine similarity between all span embeddings. Merge pairs above merge threshold (AdaptationState: `recohereThreshold`). Handles divergent thinking where the text leaves a topic, discusses something else, then returns. Scope: within a single text position only. Cross-source knowledge accumulation is working memory's job.

**Not asking**: Whether to merge spans across different sources.

#### Input
```json
{
  "spans": [
    {"spanId": "span_0", "sentenceIds": ["S1", "S2"], "text": "ObjectBox uses single-writer..."},
    {"spanId": "span_1", "sentenceIds": ["S3", "S4"], "text": "The button placement feels wrong..."},
    {"spanId": "span_2", "sentenceIds": ["S5", "S6"], "text": "Back to ObjectBox, the sync layer..."}
  ]
}
```

#### Output
```json
{
  "spans": [
    {"spanId": "span_0", "sentenceIds": ["S1", "S2", "S5", "S6"]},
    {"spanId": "span_1", "sentenceIds": ["S3", "S4"]}
  ],
  "merges": [{"merged": ["span_0", "span_2"], "similarity": 0.87}],
  "latencyMs": 15
}
```

#### Metrics (aggregate)
| Metric | Formula | Healthy | Red Flag |
|--------|---------|---------|----------|
| `merge_rate` | merges / input spans | 0-20% | > 40% |


#### Generation Prompt (Golden Data)

```
Read the concept spans for each text position. Merge adjacent spans that discuss the same concept.

Rules:
- Only merge adjacent spans within the same text position.
- Merge when two spans are clearly about the same sub-topic and were over-split by cohere.
- Most spans pass through unchanged. Healthy merge rate: 0-20%.
- Record each merge with reason.

Input: spans array per text position.
Output: results array, one entry per text. Each entry: spans array (possibly fewer) + merges array.
```

#### Review Screen
Two span texts side by side. Similarity score displayed between them. Pre-selected decision (merge/keep separate). Reviewer confirms or overrides. Arrow keys to advance. Only pairs near threshold surfaced for review.

#### Implementation
**Model**: Same `bert-wiki-paragraphs` (110M ONNX) used by cohere. Encode each span, compute pairwise cosine similarity.
O(n^2) on spans, not sentences. 10-15 spans per source = ~100 comparisons at ~3ms each = ~300ms.
**AdaptationState**: `recohereThreshold` (float).

#### Training
Shares model and training with cohere. No separate training needed.

## Stage 5: Filter

**Question**: Is this span anything, or is it conversational noise?
**Operation**: Compute heuristic features from span text. Run classification model on text + features. Score 0.0 (noise) to 1.0 (substantive). Compare against threshold (AdaptationState: `filterThreshold`, default 0.35). Deterministic fast-path: `wordCount < 3 AND NOT hasNamedEntity` skips without model call.

**Not asking**: Is this novel relative to working memory? (dedup). Is this a complete thought? (cohere/recohere). What type of knowledge? (decontext). Will this last? (working memory decay). Is this redundant? (dedup).

#### Input
```json
{
  "spanId": "span_3",
  "text": "ok sounds good let me think about that",
  "features": {
    "wordCount": 8,
    "sentenceCount": 1,
    "lexicalDensity": 0.0,
    "hasNamedEntity": false,
    "hasCausalMarker": false,
    "questionRatio": 0.0
  }
}
```

**Heuristic features** (computed deterministically, included as model input):

| Feature | Type | Computation | Signal |
|---------|------|-------------|--------|
| `wordCount` | int | whitespace split count | <5 with no entities = almost certainly noise |
| `sentenceCount` | int | sentence count in span | single-sentence spans more likely filler |
| `lexicalDensity` | float | content words / total words | "ok sure" = 0.0, technical text = 0.5-0.7 |
| `hasNamedEntity` | bool | capitalized multi-char tokens, code refs, technical terms | near-perfect substantiveness indicator |
| `hasCausalMarker` | bool | "because", "so that", "in order to", "therefore", "since" | explanations are inherently substantive |
| `questionRatio` | float | question sentences / total sentences | all-questions may not be decomposable alone |

#### Output
```json
{
  "spanId": "span_3",
  "score": 0.12,
  "decision": "skip",
  "latencyMs": 4
}
```

#### Metrics (aggregate)
| Metric | Formula | Healthy | Red Flag |
|--------|---------|---------|----------|
| `skip_rate` | skipped / total spans | 5-50% | > 80% |


#### Evaluation Rubric (for human labeling, not runtime)
| Dimension | Question |
|-----------|----------|
| **Substantive** | Contains any claim, fact, decision, preference, or description? |
| **Specific** | Concrete enough to decompose into at least one proposition? |

Both yes = extract. Either no = skip. Frontier model applies rubric first. Human verifies disagreements and borderline cases.

#### Generation Prompt (Golden Data)

```
Read the spans (with resolved text) for each text position. Label each span extract or skip.

Rules:
- Extract = durable knowledge, decisions, designs, constraints, preferences, specific metrics.
- Skip = ephemeral, trivial, generic, pleasantries, meta-text, discourse scaffolding.
- SKIP these patterns:
  - "Would you like to explore..."
  - "Let me know if..."
  - Follow-up question lists
  - Offers of further exploration
  - "Here are some options we could look at..."
  These are dialogue management, not knowledge.
- Healthy skip rate: 5-50%.

Input: spans with resolved sentence text per text position.
Output: results array, one entry per text. Each entry: decisions array (spanId + label + extractScore).
```

#### Review Screen
Span text displayed. Filter score and decision shown. Heuristic feature values alongside. Reviewer confirms extract/skip via tab toggle. Arrow keys to advance. Borderline scores (0.3-0.5) surfaced first.

#### Implementation
**Model**: DeBERTa-v3-small (44M) with binary classification head. Input = [CLS] embedding concatenated with heuristic feature vector.
**AdaptationState**: `filterThreshold` (float, default 0.35). ↑ decontext produces 0 propositions. ↓ user flags missing knowledge from skipped span.
**Latency**: ~3-5ms per span. Fast-path skips in <1ms.

#### Training
Follows generic SLM Training Process (see section above).
- **Bootstrap**: 200+ labeled spans (stratified). SetFit contrastive fine-tune (30 sec). Target: F1 90%+.
- **Active learning**: Borderline scores (0.3-0.5) routed to review. Expected: F1 90% to 95%+ after 500 corrections.
- **Labeler**: Claude Code applies rubric directly. No external LLM calls.

## Stage 6: Decontextualize

**Question**: What self-contained, atomic propositions does this span express?
**Operation**: Three jobs in order:
1. **Coreference resolution**: Replace pronouns and references ("it", "this approach", "that thing") with concrete entity names from the entity list.
2. **Decomposition**: Split the span into 0-N atomic propositions. Each proposition contains exactly one claim.
3. **Bare assertive rewrite**: Strip all epistemic framing. No "The user...", "The assistant...". Write the claim itself. (See Source-Agnostic Principle above.)

Assign scope (session/project/life) and type (learning/project/exploration).

**Not asking**: Whether to extract this span (filter decided). Whether this is redundant (dedup decides after). What entities are mentioned (entity resolution is post-encoder).

#### Input
```json
{
  "spanId": "span_0",
  "text": "So we decided to use it because it supports all six platforms. The single writer model means we need queue coordination.",
  "surroundingContext": "...previous and next span text...",
  "entityList": ["ObjectBox", "Flutter", "Everything Stack", "Supabase"]
}
```

#### Output
```json
{
  "spanId": "span_0",
  "propositions": [
    {
      "content": "ObjectBox is the persistence layer for Everything Stack because it supports all six target platforms.",
      "scope": "project",
      "type": "project",
      "sourceIds": ["S1"]
    },
    {
      "content": "ObjectBox uses a single-writer model that requires queue coordination for concurrent write operations.",
      "scope": "project",
      "type": "learning",
      "sourceIds": ["S2"]
    }
  ],
  "latencyMs": 800
}
```

#### Metrics
| Metric | Formula | Healthy | Red Flag |
|--------|---------|---------|----------|
| `props_per_span` | propositions / extract spans | 1-8 | 0 or > 15 |
| `avg_prop_words` | proposition word count | 10-25 | < 5 or > 40 |
| `compound_rate` | props with 3+ commas OR 2+ "and"s OR semicolons / total | < 10% | > 20% |
| `compression_ratio` | span words / proposition count | 8-30x | < 4x or > 50x |

Bug check (hard fail, not health range):
- `epistemic_rate` must be 0%. Any "The user/speaker/assistant" = retry.


#### Evaluation Rubric (for human labeling)
| Dimension | Question |
|-----------|----------|
| **Self-contained** | Understandable without the source text? No dangling pronouns or references? |
| **Atomic** | Contains exactly one claim? Could not be split further? |
| **Faithful** | Accurately represents what the source said? No hallucinated details? |
| **Bare assertive** | Written as a standalone claim? No "The user/assistant..." framing? Passes the "It is known that..." test? |
| **Complete** | All extractable knowledge from the span captured across all propositions? |

Frontier model applies rubric first. Human verifies disagreements.

#### Generation Prompt (Golden Data)

```
Read the extract spans (spans that passed filter). For each span, produce self-contained
propositions in bare assertive form.

Rules:
1. Bare assertive form. Every proposition is a standalone knowledge claim.
   Test: "It is known that [proposition]" must read naturally.
   NEVER use "The user", "The speaker", "The assistant", "The person".

2. Atomic. ONE fact per proposition.
   - BAD: "Labor requires 12,000 hours for core and 5,500 for revenue activities."
     GOOD: "Core fleet operations require 12,000 labor hours annually."
           "Revenue activities require 5,500 labor hours annually."
   - BAD: "The system uses a 1:18 ratio and costs $63.75/month."
     GOOD: "The proposed vehicle-to-user ratio is 1:18."
           "The estimated per-capita cost is $63.75 per month."
   Test: can you remove any clause without losing a DIFFERENT fact? If yes, split.

3. Self-contained. Each proposition understandable without the source text.
   Replace pronouns with referents. Include specific numbers, distances, costs.
   - BAD: "A ridesharing obligation exists."
     GOOD: "Vehicle users must provide ridesharing within 10 miles of their destination."

4. Grounded. Every proposition traces to specific source sentences via sourceIds.

5. Capture all facts. Every constraint, metric, cost, design decision, and preference
   in the source must appear. Do not summarize away specifics.

6. Track evolution. If the text revises a design, produce propositions for
   BOTH the original and the revision. Mark the revision with type "correction".

Input: extract spans with resolved sentence text.
Output: propositions array (content + scope + type + sourceIds).

scope values: session, project, life
type values: decision, design, constraint, preference, exploration, domain, hypothesis, correction
```

#### Review Screen
Source span text on top. Propositions listed below, each with scope/type tags. Reviewer can: confirm all, flag individual propositions (not self-contained, not atomic, not faithful), mark span as incomplete (missing knowledge). Arrow keys to advance to next span.

#### Implementation
**Model**: Groq LLM (8B). **Permanent LLM stage.** Generative rewriting requires 3B+ minimum (Choi et al. 2021). Sub-1B cannot do this.
**Input per span**: target span text + 2-3 surrounding sentences + entity list from working memory (~200 tokens total).
**Per-span, not batch**: keeps context small, enables future SLM transition to T5-3B.
**Also callable from dedup**: when bidirectional entailment detected, dedup routes the pair here for canonical rewrite.

#### Training
**Stays on LLM.** Prompt optimization only. Flagged propositions drive PromptImprovementLoop.
**Future SLM**: T5-3B fine-tuned. Requires ~1000 (span, propositions) pairs.

## Stage 7: Dedup

**Question**: Does this proposition duplicate, contradict, or refine anything already in working memory?
**Operation**: For each new proposition, run NLI cross-encoder against every working memory proposition. Classify each pair as: no match, entailment (merge), or contradiction (supersede). On merge: route both propositions to decontext for canonical rewrite. When working memory is empty, all propositions are added directly.

**Not asking**: Whether this is substantive (filter decided). What entities are mentioned (entity resolution is post-encoder). Whether this is "important": all propositions that reach dedup have passed filter and decontext.

#### Input
```json
{
  "propositions": [
    {"content": "ObjectBox uses a single-writer model requiring queue coordination.", "sourceIds": ["S2"]}
  ],
  "workingMemory": [
    {"uuid": "p_01", "content": "ObjectBox requires queue coordination for concurrent writes."},
    {"uuid": "p_02", "content": "Flutter supports six target platforms."}
  ]
}
```

#### Output
```json
{
  "diff": {
    "added": [],
    "superseded": [{"oldUuid": "p_01", "newUuid": "p_03", "reason": "bidirectional_entailment"}],
    "rewritten": [{"oldUuid": "p_01", "mergedInto": "p_03"}]
  },
  "comparisons": [
    {"new": "p_new", "existing": "p_01", "entailment": 0.91, "contradiction": 0.01, "decision": "merge"},
    {"new": "p_new", "existing": "p_02", "entailment": 0.08, "contradiction": 0.02, "decision": "no_match"}
  ],
  "latencyMs": 6
}
```

#### Metrics (aggregate)
| Metric | Formula | Healthy | Red Flag |
|--------|---------|---------|----------|
| `merge_rate` | entailments / total propositions | 5-30% | 0% after text 3 or > 60% |
| `wm_growth_rate` | net added / total propositions | 40-90% | 100% always |


#### Evaluation Rubric (for human labeling)
| Dimension | Question |
|-----------|----------|
| **Match correctness** | Entailment/contradiction/no-match classification correct for this pair? |
| **Merge quality** | When merged, does the canonical rewrite preserve information from both? |
| **No false merges** | Are non-duplicate propositions correctly kept separate? |

Frontier model applies rubric first. Human verifies.

#### Generation Prompt (Golden Data)

```
Read all propositions from this source AND the prior working memory.
Compare every proposition against every other. Label each pair.

Rules:
- Exhaustive comparison. N*(N-1)/2 pairs. Label ALL of them.
  Incomplete coverage means the SLM learns to miss duplicates.
- bidirectional_entailment: same claim, different words. One is redundant.
- forward_entailment: A entails B but not vice versa. A is more general.
- contradiction: A and B conflict (proposed then rejected, original then revised).
  For each contradiction, determine which proposition is SUPERSEDED and which SUPERSEDES.
  The superseded prop is archived from working memory.
- no_match: different facts.

Common missed patterns:
- "X labor is done by the community" + "Fleet maintained through community efforts" = forward_entailment.
- Design proposed in text 0 + rejection in text 3 = contradiction.
- Same fact restated across texts = bidirectional_entailment.

Input: all propositions from this source + prior working memory propositions.
Output: pairs array (all N*(N-1)/2) + resolutions array (one per contradiction).

Resolution format:
- supersededIndex: the obsolete/rejected proposition.
- supersededBy: the proposition that replaces or rejects it.
- reason: brief explanation.
When one rejection supersedes multiple proposals, create a resolution for EACH.
```

#### Review Screen
New proposition on left. Matched WM proposition on right. NLI scores (entailment, contradiction, neutral) displayed. Pre-selected decision shown. If merge: canonical rewrite displayed below. Reviewer confirms or overrides. Arrow keys to advance. Only pairs near threshold surfaced.

#### Implementation
**Model**: `nli-deberta-v3-xsmall` (22M). Cross-encoder: (proposition A, proposition B) → entailment/contradiction/neutral scores.
**Merge trigger**: bidirectional entailment > threshold → route to decontext for canonical rewrite.
**Contradiction trigger**: contradiction > threshold → supersede old with new.
**Inference**: N new propositions x M working memory entries x ~3ms each.
**AdaptationState**: `entailmentThreshold` (float), `contradictionThreshold` (float).

#### Training
**Fine-tuning**: Trigger: >10% correction rate across 50+ reviewed pairs. Golden data: (proposition_a, proposition_b, correct_decision) from review. Expected improvement: accuracy from ~80% to 90%+.

## Pipeline Ordering Rationale

The order is load-bearing. Each stage depends on the previous stage's output form:

| Stage | Requires from previous | Cannot move because |
|-------|----------------------|-------------------|
| Normalize | Raw text | Must clean before splitting |
| Segment | Clean punctuated text | Cannot split unpunctuated text reliably |
| Cohere | Sentence list | Needs atomic units to score adjacency |
| Recohere | Initial span list | Needs cohere boundaries before merging across gaps |
| Filter | Final spans | Must have coherent spans to score |
| Decontext | Filtered extract spans + WM entity list | Needs clean spans and entity context for pronoun resolution |
| Dedup | Atomic propositions + WM state | Cannot compare messy span text against clean WM propositions |

**Dedup cannot move before decontext** because dedup compares propositions (atomic, self-contained) against propositions. Before decontext, only messy multi-claim span text exists.

**Filter is an optimization, dedup is correctness.** Removing filter entirely works. It just wastes LLM calls on noise spans. Removing dedup breaks working memory with duplicates.

## SLM Training Process (Generic)

**No external LLM calls.** Claude Code applies each stage's evaluation rubric directly to create golden labels. No Groq, no frontier model API. The labeler is the development agent.

Every SLM-backed stage follows the same training loop. The stage defines two things: its **rubric** (what dimensions to evaluate) and its **golden data format** (input/output pairs from the pipeline). Everything else is generic.

### Training Loop

```
1. COLLECT — Gather stage input/output pairs from golden pipeline runs
2. LABEL  — Claude Code applies the stage's rubric to each pair (no external LLM)
3. BASELINE — Run pre-trained (zero-shot) SLM on the same inputs, measure accuracy against labels
4. TRAIN  — Fine-tune SLM on labeled data (SetFit contrastive / LoRA / full retrain)
5. EVALUATE — Run fine-tuned SLM on held-out split, measure accuracy improvement over baseline
6. SHIP or ITERATE — If improved: export ONNX, deploy. If not: analyze failures, relabel, retrain.
```

**Human enters at step 6**, reviewing only after Claude Code has confirmed improvement. The review UI surfaces borderline cases and disagreements, not the full dataset.

### Stage Contract for Training

Each trainable stage provides:

| Contract Item | What it defines | Example (Filter) |
|--------------|----------------|-------------------|
| **Rubric** | Evaluation dimensions with yes/no questions | Substantive? Specific? |
| **Decision rule** | How dimension answers map to labels | Both yes = extract, either no = skip |
| **Golden input** | What the SLM sees at inference time | Span text (+ optional heuristic features) |
| **Golden output** | The label the SLM should produce | "extract" or "skip" |
| **Metrics** | How to measure quality | Precision, recall, F1 per class |
| **Improvement threshold** | When fine-tuned model is ready | F1 > baseline + 5% |

### Label Format (All Stages)

```json
{
  "index": 0,
  "input": "the text or pair the SLM will classify",
  "label": "the correct classification",
  "dimensions": {"dim1": true, "dim2": false},
  "confidence": "high|borderline",
  "rationale": "brief reason for this label",
  "labeledBy": "claude-opus-4|human"
}
```

### Data Splits

| Split | Size | Purpose |
|-------|------|---------|
| Train | 70% | Fine-tuning data |
| Validation | 15% | Hyperparameter selection, early stopping |
| Test | 15% | Final accuracy measurement (never trained on) |

Stratified by label. Borderline-confidence examples weighted toward validation/test for harder evaluation.

### CPU Training Sizing (SetFit)

**Terminology:**
- **SetFit**: Sentence Transformer Fine-Tuning. Few-shot classifier. Fine-tunes a sentence transformer via contrastive learning, then trains a logistic regression head on embeddings. 8-64 examples per class. No prompts, no large LM.
- **Contrastive pair**: Two texts shown together. Same-class pairs pull embeddings closer. Different-class pairs push them apart.
- **num_iterations**: Pairs generated per training sample. Higher = more diversity = better embeddings, but linearly more compute.
- **batch_size**: Pairs per forward/backward pass. Larger = fewer steps, more memory. 16 is standard for CPU.
- **Step**: One forward + backward + weight update on one batch. Total steps = total pairs / batch_size.
- **Epoch**: One full pass through all pairs. SetFit uses 1 epoch. Pair generation already provides diversity.

**Sizing math:**

Pair count formula: `num_iterations * num_train_samples` per class.
DeBERTa-v3-small: ~24s/step on CPU (batch=16, no GPU).

| Train samples | num_iterations | Total pairs | Steps (batch=16) | Wall time (CPU) |
|---------------|---------------|-------------|-------------------|-----------------|
| 1450          | 20            | 58,000      | 3,625             | ~24 hours       |
| 128 (64/class)| 20            | 2,560       | 160               | ~64 min         |
| 128 (64/class)| 5             | 640         | 40                | ~16 min         |
| 32 (16/class) | 5             | 320         | 20                | **8 min (measured)** |

**16/class baseline results** (32 train, 1673 eval):

| Class | Precision | Recall | F1 |
|-------|-----------|--------|----|
| skip | 0.46 | 0.85 | 0.60 |
| extract | 0.97 | 0.83 | 0.89 |
| weighted avg | 0.89 | 0.83 | 0.85 |

- Skip precision low (0.46): over-predicting skip. Only 16 skip examples = not enough variety.
- Extract precision high (0.97): model learned real signal from just 32 examples.
- Fix: scale to 64/class for more skip variety.

SetFit is few-shot by design. Use **fixed train-per-class**, not percentage split:
- Start with 16/class (32 total) to validate the pipeline end-to-end (~8 min).
- Scale to 64/class once pipeline is confirmed working (~16 min).
- Remaining labels become the eval set. Large eval = reliable metrics.
- Start with `num_iterations=5`. Increase to 20 only if quality is insufficient.
- `batch_size=16` is the sweet spot. 32 gives marginal speedup, 8 is slower.
- Full labeled set is an evaluation asset first, training asset second.

## End-to-End Pipeline Evaluation

Per-stage rubrics measure stage correctness. This section measures pipeline outcome: given a raw source, did the pipeline produce the right working memory?

### Why Per-Stage Is Not Enough

- Errors compound. A bad cohere grouping causes a bad filter decision causes a bloated decontext output that dedup cannot fix.
- Per-stage golden data validates each stage in isolation. No check asks "is the final working memory correct?"
- Dedup is catching 6.8% average reduction across 16 conversations. Either upstream stages are near-perfect (unlikely) or dedup is under-performing.

### End-to-End Rubric

For each source's final working memory, evaluate every proposition on six dimensions:

| Dimension | Question | Failure means |
|-----------|----------|---------------|
| **Grounded** | Is this proposition supported by the source text? | Decontext hallucinated or over-inferred |
| **Atomic** | Does this contain exactly one claim? | Decontext under-decomposed |
| **Bare assertive** | Written as a standalone claim? No "The user/assistant..." framing? | Decontext used epistemic framing instead of bare proposition |
| **Non-redundant** | Is this the only proposition expressing this idea in WM? | Dedup missed a duplicate |
| **Durable** | Will this matter beyond this session? | Filter was too permissive |
| **Self-contained** | Understandable without the source text? No dangling references? | Decontext left unresolved pronouns |

Each dimension is binary yes/no per proposition. No partial credit.

### Aggregate Metrics

Computed from the per-proposition dimension scores:

| Metric | Formula | Healthy | Problem |
|--------|---------|---------|---------|
| **Precision** | propositions with all 6 dimensions passing / total WM size | >85% | <70% means too much junk in WM |
| **Redundancy rate** | propositions failing non-redundant / total WM size | <10% | >15% means dedup is broken |
| **Durability rate** | propositions passing durable / total WM size | >70% | <50% means filter is too permissive |
| **Bare assertive rate** | propositions passing bare assertive / total WM size | >95% | <80% means decontext prompt needs fixing |
| **Compression ratio** | source word count / WM proposition count | 50-200 words/prop | <30 (over-extracting) or >500 (under-extracting) |

### Recall Check

Precision is per-proposition (score what's in WM). Recall is per-source (what's missing from WM).

After scoring all propositions, the reviewer reads the source texts and answers:
- "Is any important knowledge from this source missing from working memory?"
- Each missing item is logged as a recall failure with the text index it came from.

Recall failures trace back to specific stages:
- Filter skipped a substantive span (filter too aggressive)
- Decontext dropped a claim from a span (decontext incomplete)
- Normalize/segment/cohere mangled the source text (upstream corruption)

### Failure Attribution

Every failing proposition maps to the stage that caused the failure:

| Failure | Responsible stage |
|---------|------------------|
| Not grounded | Decontext (hallucinated) |
| Not atomic | Decontext (under-decomposed) |
| Not bare assertive | Decontext (epistemic framing) |
| Redundant | Dedup (missed duplicate) |
| Not durable | Filter (should have skipped the source span) |
| Not self-contained | Decontext (unresolved reference) |
| Missing from WM | Filter (skipped) or Decontext (dropped) or upstream (corrupted) |

This closes the loop: end-to-end evaluation produces per-stage improvement signals without re-running per-stage rubrics.

## End-to-End Human Review Process

Same design principles as per-stage review: low cognitive burden, binary decisions, borderline-first surfacing.

### Review Flow

```
1. Auto-evaluate: Claude Code scores every proposition on 5 dimensions
2. Triage: Sort propositions into PASS (all 5 pass), FAIL (any fail), BORDERLINE (close calls)
3. Surface: Show FAIL and BORDERLINE to human reviewer. PASS items are spot-checked only.
4. Review: Human confirms or overrides each dimension per proposition (yes/no toggle)
5. Recall: Human reads source texts, flags missing knowledge
6. Output: Scored working memory + recall gaps + per-stage failure counts
```

### Auto-Evaluation Protocol

Claude Code evaluates every proposition before human review. For each proposition:

1. **Grounded**: Search source text for evidence supporting the claim. If no matching passage found within the source, mark NO.
2. **Atomic**: Check if the proposition contains conjunctions joining independent claims ("X and Y" where X and Y are separable). If splittable, mark NO.
3. **Bare assertive**: Check if the proposition contains "The user", "The assistant", or any attribution. Apply the "It is known that..." test. If it reads as a report about someone rather than a claim about the world, mark NO.
4. **Non-redundant**: Compare against all other WM propositions. If bidirectional entailment with another proposition (same claim, different words), mark NO and record the duplicate ID.
5. **Durable**: Check scope. Session-scoped propositions in the final WM of a multi-text source are suspect. Ephemeral scheduling ("has 5 hours today") = NO. Decisions and learnings = YES.
6. **Self-contained**: Check for unresolved pronouns ("it", "this", "that") or references requiring source context ("the approach mentioned above"). If found, mark NO.

## Encoder Scope Boundary

The encoder produces propositions and working memory diffs. **It does not**:
- Do entity resolution (post-encoder, converts propositions to facts)
- Write to the knowledge store (entity resolution does this)
- Determine long-term importance (working memory decay handles this)
- Resolve entities across sources (entity resolution + knowledge store)

## Future Work (not in current build)

### Entity Resolution (post-encoder)
Runs after encoder updates working memory. Converts propositions to facts.
Three-stage: GLiNER NER (50M, entity mention detection) → HNSW blocking (candidate retrieval) → NLI cross-encoder (match confirmation).
The boundary where propositions become facts with entity links and temporal metadata.

### Knowledge Store
All persisted facts with entity links and temporal metadata. Append-only with supersession.

### Consolidation
Periodic background dedup of the knowledge store grouped by entity. Catches redundancies between propositions that were never co-resident in working memory.

### Global Coherence Across Sources
Working memory naturally accumulates cross-source knowledge. Recohere operates within a single text position. Cross-source topic merging is a knowledge store concern, not an encoder concern.
